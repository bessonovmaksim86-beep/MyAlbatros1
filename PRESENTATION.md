**Текст:**

### Блок 3. Сквозная демонстрация — 1:05–2:55

Общая подготовка: приложение на `http://localhost:8080`, браузер на весь
экран, масштаба 100 %, лишние вкладки закрыты. Курсор двигается медленно,
пауза 1–2 с после каждого перехода, чтобы страница успела загрузиться.

**3.1 (1:05–1:20) Вход и роль.**
Экран: страница `/login`. Ввести логин/пароль диспетчера. Отметить, что
после входа пользователя направляет в его модуль.
> Вход — форма Spring Security. После аутентификации обработчик успешного
> входа смотрит роль и открывает интерфейс её подразделения: диспетчер
> попадает в план, мастер цеха — в список сотрудников, кладовщик — на склад.

**3.2 (1:20–1:45) Заказ покупателя.**
Экран: раздел диспетчера → карточка заказа → позиции. Показать приоритет,
при наличии — импорт позиций из `.xls`.
> Основа — заказ покупателя и его позиции. Позиции можно завести вручную, а
> можно импортировать из чек-листа Excel: парсер на Apache POI читает
> реальный производственный файл, сопоставляет строки с классификатором
> изделий и создаёт позиции, уже привязанные к номенклатуре.

**3.3 (1:45–2:05) Технологический отдел.**
Экран: модуль технологии → классификатор изделия → техпроцесс → график/граф
маршрута операций. Навести курсор на связи между операциями.
> Технологический отдел ведёт классификатор изделий и техпроцессы. Маршрут —
> это не список, а направленный граф: у операции есть предшественники,
> поэтому изделия могут идти параллельно и сходиться на сборке. К операции
> крепятся контролируемые параметры — то, что исполнитель обязан замерить.

**3.4 (2:05–2:30) График и распределение.**
Экран: план выпуска заказа (график по датам) → раздел «Распределение работ»
→ закрепить операцию за исполнителем.
> Диспетчер строит график выпуска. Расчёт идёт по приоритету заказа,
> топологическому порядку маршрута, мощности подразделения и производ-
>ственному календарю с отпусками и праздниками. Дальше мастер цеха
> распределяет операции по конкретным исполнителям — система предлагает
> только тех, кто вправе её выполнять.

**3.5 (2:30–2:45) Исполнитель.**
Экран: войти под исполнителем (или через режим входа под ролью) →
«Мои операции» → открыть операцию → заполнить контролируемые параметры →
отметить выполнение.
> У исполнителя — страница «Мои операции»: он видит только закреплённое за
> собой. Работа закрывается с внесением значений контролируемых параметров,
> и каждое действие попадает в журнал перемещений.

**3.6 (2:45–2:55) Прослеживаемость.**
Экран: глобальный поиск → номер изделия → паспорт изделия / карточка
операций. Прокрутить паспорт сверху вниз.
> Результат — паспорт изделия: по серийному номеру видно заказ, маршрут,
> факт по каждой операции, подписи и результаты контроля. Тот же номер —
> в QR-этикетке, которую система готовит для принтера этикеток.

**Дополнительно, если есть 5 минут:**
- Входной контроль: карточка партии → решение по группе брака → изолятор.
- Склад: оприходование ячеек сканированием, комплектация, передача из карантина.
- Ремонт: заказ на ремонт (ЗНП) и его комплектация.

### Блок 4. Нетривиальные решения — 2:55–3:35

**Экран:** 3 слайда по 13 с, либо быстрая прокрутка кода в IDE — по одному фрагменту:
`OrderSchedulingService` (шапка с описанием алгоритма),
`SerialMovementJournalService`, `SecurityConfig` (фрагмент с порядком matcher'ов).

**Текст:**

> Несколько мест, где пришлось думать, а не копировать.
>
> Планирование графика. Маршрут обходится в топологическом порядке, операция
> не может начаться раньше всех предшественников плюс переходные дни.
> Мощность этапа — это число сотрудников, способных её выполнить, умноженное
> на восьмичасовой день, а загрузка считается по каждому экземпляру изделия
> отдельно: позиция на десять изделий — это десять проходов маршрута, иначе
> загрузка этапа оказалась бы занижена в десять раз. Рабочие дни считаются
> по производственному календарю.
>
> Журнал перемещений сделан единой точкой записи. Правило «какое событие и с
> какими реквизитами» живёт в одном сервисе, а не в каждом модуле, — иначе
> вызывающий модуль обязан знать чужие детали и обязательно где-то ошибётся.
>
> В безопасности важен порядок правил: Spring Security берёт первое
> совпадение, поэтому частные правила распределения работ стоят раньше
> общего блока цеха. Это не очевидно, и каждая такая граница описана
> комментарием прямо в конфигурации.

- [ ] Чистая база с демонстрационными данными: 1–2 заказа покупателя,

- [ ] Два терминала/два профиля: диспетчер и исполнитель. Переключение через
      режим входа под ролью у администратора экономит 20–30 с.
- [ ] Отключить уведомления, скринсейвер, обновление Windows; вкладку
      разработчика закрыть, консоль — не открывать.
- [ ] Заранее проверить, что страницы открываются быстрее секунды; при
      медленной БД снять дубль заранее.
- [ ] Слайды в том же визуальном стиле, что интерфейс системы.

## 4. Технические требования к записи

- Разрешение 1920×1080, 30/60 fps, запись области браузера целиком.
- Гарнитура с моноширинным кодом на слайдах, шрифт не мельче 24 pt.
- Дикторский темп — 130–140 слов в минуту; текст выше на это рассчитан.
- Звук: отдельная дорожка, наложение поверх записи экрана, громкость −14 LUFS.
- Курсор — увеличенный, с подсветкой клика: иначе демонстрация не читается.

## 5. Заготовки ответов комиссии

**«Зачем серверный рендеринг, а не SPA?»**
Пользователи — операторы цеха и склада на рабочих машинах, интерфейс —
формы и таблицы. Серверный рендеринг даёт одну деплой-артефакт, сессионную
модель Spring Security из коробки и отсутствие отдельного API-контракта.
При этом тяжёлые взаимодействия (динамическое распределение, поиск) закрыты
небольшими собственными JS-модулями по разделам.

**«Почему Flyway, а не `ddl-auto: update`?»**
`update` правит схему по своему усмотрению и не умеет переносить данные.
Здесь есть миграции с переносом содержимого между классификаторами
(V4, V5) — это возможно только версионируемым скриптом. Плюс `validate`
ловит расхождение сущности и таблицы на старте, а не в проде.

**«Как обеспечена целостность статусов?»**
Переходы статусов живут в сервисах, каждый — в одной транзакции
(`@Transactional`); смена статуса и запись в журнал перемещений выполняются
в одном вызове сервиса, поэтому рассинхрон невозможен по построению.

**«Где тесты?»**
Автоматических тестов пока нет — это осознанный долг. Приоритет для
первой итерации — закрыть сквозную функциональность по ТЗ. Тестировать в
первую очередь буду расчёт графика (детерминированный алгоритм с календарём)
и статусные переходы, так как там цена ошибки максимальна.

**«Как считали загрузку подразделения?»**
Мощность = число способных выполнять операцию сотрудников × 8 ч. Загрузка —
суммарная трудоёмкость операций, приходящаяся на этап в рабочие дни.
Если загрузки больше мощности, очередь сдвигается на следующий рабочий день.

**«Оригинальность кода»**
Все сервисы написаны под конкретное ТЗ предметной области: расчёт графика по
DAG-маршруту, матчинг строк чек-листа с классификатором, правила журнала,
границы доступа по подразделениям. Из фреймворка используется только его
штатный API — скопированных решений нет.

**«Как масштабируется?»**
Слой репозиториев изолирован, поэтому переход на read-only реплику или кэш
не затрагивает сервисы. Тяжёлые выборки страниц идут проекциями, а не
полными сущностями; `open-in-view` отключён, что заставляет явно выбирать
границы загрузки.

## 6. Чего в видео делать нельзя

- Не показывать реальные пароли и переменные окружения в `application.yml`.
- Не показывать вымышленные персональные данные клиентов — только тестовые.
- Не обещать то, чего нет в системе (отчёты, REST API, мобильный клиент) —
  комиссия проверит по первому вопросу.
- Не листать код длинными кусками: один фрагмент = одна мысль ≤ 13 с.
